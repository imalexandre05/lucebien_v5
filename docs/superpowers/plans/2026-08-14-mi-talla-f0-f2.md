## 0. Decisión de nomenclatura SQL: prefijo `mt_` (recomendado)

Verifiqué las 66 migraciones: no existe ninguna tabla `medicion`, `medicion_real`, `consentimiento`, `medicion_imagen` ni nada `mt_*`. Aun así, **recomiendo prefijo `mt_`** por tres razones concretas:

1. **`clientes` del ERP ya existe** (0001_init.sql:53, con columna `medidas jsonb`) y sus `id` NO son usuarios de Supabase Auth. En Mi Talla, `cliente_id = auth.uid()`. Una tabla pelada `medicion(cliente_id)` junto a `clientes(id)` invita a un JOIN que sería un bug semántico. El prefijo hace visible que son dominios distintos.
2. Las 53 tablas del ERP conviven en `public` sin namespace; con `mt_` toda auditoría RLS del módulo se filtra con `like 'mt\_%'` (útil para el guard CI y para el bloque de verificación).
3. `consentimiento` y `medicion` son nombres que el ERP podría querer para sí (confección a medida futura). No hipotecar los nombres genéricos.

Tablas: `mt_medicion`, `mt_medicion_real`, `mt_consentimiento`, `mt_medicion_imagen`, `mt_config`. Bucket storage: `mi-talla`.

Divido el SQL en **dos migraciones**: `0067_mi_talla_esquema.sql` (F1: tablas + RLS + seeds) y `0068_mi_talla_storage.sql` (F2: bucket + policies de storage). Razón: la cadena sigue siendo única y ordenada, pero las policies sobre `storage.objects` tienen riesgo de fallo por ownership en Supabase hosted (ver Riesgo R1) y no deben poder bloquear F1; además F1 no necesita storage.

**T0.3 — Contornos Ramanujan (TDD)**

Implementación `lib/medidas/contornos.ts` (las formas exactas importan — el spec advierte que circulan mal transcritas):
```ts
/** Ramanujan I: π[3(a+b) − √((3a+b)(a+3b))] */
export function perimetroRamanujanI(a: number, b: number): number {
  return Math.PI * (3 * (a + b) - Math.sqrt((3 * a + b) * (a + 3 * b)))
}
/** Ramanujan II con h = ((a−b)/(a+b))²: π(a+b)[1 + 3h/(10+√(4−3h))] */
export function perimetroRamanujanII(a: number, b: number): number {
  const h = ((a - b) / (a + b)) ** 2
  return Math.PI * (a + b) * (1 + (3 * h) / (10 + Math.sqrt(4 - 3 * h)))
}
/** Adaptativo (Montazerian & Fol Leymarie 2022): eje mayor ≤ 3× menor → I; más achatado → II */
export function perimetroElipse(a: number, b: number): number {
  const [may, men] = a >= b ? [a, b] : [b, a]
  return may <= 3 * men ? perimetroRamanujanI(may, men) : perimetroRamanujanII(may, men)
}
```

## 7. Riesgos de implementación nuevos (no listados en el spec)

- **R1 — Policies de `storage.objects` pueden fallar por ownership** en Supabase hosted (`must be owner of table objects`): no hay precedente en las 66 migraciones (verificado). Mitigado con migración separada 0068 + fallback Dashboard documentado (A5).
- **R2 — Crecimiento basura de `auth.users` por sesiones anónimas**: cada visitante curioso crearía un usuario si la sesión se abre al montar la página; además Safari ITP borra localStorage a los ~7 días (el "anónimo que vuelve" será OTRO uid). Mitigación de diseño: sesión anónima **lazy** (solo al guardar/insertar), UI que empuja a guardar con email, y query de limpieza de anónimos huérfanos documentada en 0067.
- **R3 — `updateUser({email})` con email ya registrado** rompe el flujo feliz de conversión: hay que ramificar a `signInWithOtp` y re-insertar la medición en curso bajo el nuevo uid (T1.7); si no se maneja, el usuario ve un error críptico y la medición queda huérfana.
- **R4 — SMTP/plantillas compartidas con el ERP** (mismo proyecto Supabase): activar Resend y editar plantillas afecta los emails de reset del ERP (0049). Es mejora, pero hay que re-probar el reset del ERP tras A3.
- **R5 — Desalineación wasm↔paquete MediaPipe**: el wasm servido desde `public/mediapipe-wasm/` debe ser exactamente el de la versión npm instalada; por eso la dependencia va **pineada sin `^`** y el copiado corre en `predev`/`prebuild` desde `node_modules` (nunca commitear el wasm).
- **R6 — Tema oscuro global**: `globals.css` fuerza neutros navy; `/mi-talla` y `/taller/medir` heredan web oscura. El preview de cámara y formularios largos móviles deben diseñarse con los tokens existentes desde el día 1 — si Alexander espera estas pantallas claras, es retrabajo de CSS Modules, no de lógica (decidir antes de T1.6).
- **R7 — `mt_config` editable puede romper el parseo del cliente** (admin edita JSON a mano): `validarConfigTallas` con fallback silencioso a `CONFIG_TALLAS_DEFAULT` + warn; el default embebido y el seed deben mantenerse espejo (test que compara `CONFIG_TALLAS_DEFAULT` contra un fixture del seed).
- **R8 — Calidad del mapeo ANSUR→medidas de sastre**: `largo_saco` (regla 0.385·altura), `hombros` (+3 cm biacromial→costura) y `entrepierna` (crotchheight≈inseam) son aproximaciones estructurales, no regresión. La UI de F1 debe apoyarse en **talla** (robusta, saltos de 5 cm) y mostrar las medidas con su ±cm sin protagonismo; los pares de F2 recalibran esto — es exactamente para lo que existe `versionCalibracion`.
- **R9 — Proyecto Supabase pausado ANTES del deploy F1** (free tier, ~1 semana sin actividad): si Alexander aplica 0067 y el desarrollo tarda, el proyecto puede pausarse a mitad de F1. Revisar el dashboard antes del E2E; el keep-alive solo protege desde que hay deploy con cron.
- **R10 — Pruebas de cámara requieren HTTPS**: getUserMedia no corre en `http://<ip-local>` desde el celular; todo el ciclo de prueba F2 va contra previews de Vercel (o `next dev --experimental-https`), lo que alarga el loop de iteración — planificar sesiones de prueba en tanda, con logging visible en pantalla (no hay DevTools cómodo en iOS).
